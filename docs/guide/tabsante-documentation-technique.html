1Le produit

Une plateforme de soins qui facture sur preuve

TabSanté V2 sert les cabinets d'infirmiers libéraux (IDEL) qui soignent à domicile. Chaque cotation découle d'un acte tracé, horodaté et signé chez le patient ; l'objet suivi (plaie, dispositif, pompe…) est l'unité de traçabilité. La plateforme rend visible le travail clinique (rôle propre, observation, raisonnement) et coordonne avec l'extérieur (médecin traitant, pharmacie, laboratoire, DMP).

  • Terminal infirmier (Flutter, Android ; servi aussi en web pour la démo) : la tournée hors connexion, une main, ganté, en plein soleil. Saisir un passage doit prendre moins de temps que le soin.
  • Poste fixe (React) : au cabinet, le soir — courbes de plaie, bilans, tournées, habilitations, file de contrôle de la cotation, dossier de preuve (« la preuve d'un acte en moins de 30 secondes »).
  • API (FastAPI + PostgreSQL) : règles, immuabilité, cotation, preuve, synchronisation, journal d'audit chaîné.

Utilisateurs : IDE titulaire, IDE remplaçant·e, aide-soignant·e (AS, nursing), administration du cabinet ; indirectement le patient, le médecin traitant et le contrôleur de l'Assurance maladie. Source : PRODUCT.md, CDC V2 (docs/reference/cdc_v2_texte.txt).

Ce qui n'est pas réel aujourd'hui

Le moteur de cotation branché est un moteur de démonstration : ne jamais facturer avec. Le moteur NGAP réel est un actif TABSANTE, attendu derrière le port Moteur.
  • Authentification de développement : Keycloak + CPS / Pro Santé Connect, INSi, Vitale/FSE, DMP, MSSanté et l'hébergement HDS sont des lots ultérieurs ; chaque service externe passe par un port avec un adaptateur simulé (§15). Le mode démonstration simule aussi les cartes CPS et Vitale, la connexion et la signature par carte, l'agent de poste, le laboratoire, le DMP, l'ordonnance numérique, la visio et la géographie de la tournée (géocodage, itinéraire, trafic, météo, GPS) ; un seul registre règle leurs pannes (§15).
  • Base locale du terminal chiffrée (AES-256-GCM, clé dans le Keystore Android) ; le terminal servi en web garde sa clé dans le navigateur (démonstration seulement). TEE non utilisé ; mode kiosque écrit derrière TABSANTE_KIOSQUE, non éprouvé sur appareil.
  • Fichiers du serveur (photos, PDF, ordonnances) chiffrés au repos, mais derrière un KMS local simulé (trousseau en fichier) ; le KMS de l'hébergeur HDS reste à brancher (§8).
  • Aucune donnée réelle de patient dans le dépôt ; la démo crée un cabinet fictif, avec des coordonnées de domicile fictives.

Principes qui contraignent le code

  • Immuabilité : un acte signé ne se modifie jamais ; il se corrige par un événement motivé (correction CV-04, rectification C11), l'historique reste lisible. La base l'impose (trigger interdit_modification).
  • Une saisie, plusieurs restitutions : courbes, bilans, FHIR, preuve et cotation relisent les données signées, jamais ressaisies.
  • Le moteur décide, la plateforme tient des faits datés : aucune règle de cotation n'est dupliquée hors du moteur (EX-FA-06).
  • Hors connexion d'abord : le terminal travaille sur sa précharge et une file rejouable ; la disponibilité du serveur n'arrête aucun soin.
  • Aucun code de spécification à l'écran : les identifiants du CDC (EX-, HAB-, D-, RG…) vivent dans les commentaires et dans le champ machine regle des refus ; un test le vérifie (§16).

2Architecture

Vue d'ensemble : trois clients, une API, une base

L'API est la seule à toucher la base et les fichiers. Les deux clients internes parlent JSON en HTTPS avec un jeton d'accès JWT ; le professionnel externe passe par un portail distinct (/externe), avec un jeton QR et son identité Pro Santé Connect. Les services de l'Assurance maladie et de santé numérique, les cartes et la géographie de la tournée sont derrière des ports, aujourd'hui simulés.

Le terminal hors connexion et la synchronisation

Le terminal charge le matin tout ce qu'il faut pour la tournée (GET /terminal/precharge), travaille sans réseau, met chaque geste dans une file d'opérations dont les identifiants sont générés au terminal, et la rejoue par lots (POST /sync) dès que le réseau revient. Le serveur rend, opération par opération, un reçu ou un refus motivé ; un refus n'emporte pas les autres opérations du lot (SAVEPOINT par opération).

Services externes : des ports, des adaptateurs simulés

Chaque dépendance externe passe par une interface Python (typing.Protocol) et une instance unique choisie au démarrage. Le domaine n'appelle que le port ; un test de contrat écrit contre le port doit tourner tel quel contre l'adaptateur réel le jour où il arrive. Fiches d'interface : docs/exploitation/interfaces/.

Agent de poste : cartes et SESAM-Vitale au poste fixe

Le navigateur ne parle ni aux lecteurs de cartes ni au composant SESAM-Vitale installé sur le poste. L'agent de poste est un petit programme du poste fixe qui fait ce pont : un adaptateur de plus derrière PortSesamVitale et le port des cartes, pas un second produit. Statut : spécification (docs/exploitation/agent-de-poste.md) ; le côté serveur est construit et testé avec un agent simulé ; l'agent réel attend le choix du composant (D-07, candidat AreaFSE étudié dans docs/exploitation/interfaces/sesam-vitale.md) et l'agrément CNDA propre à TabSanté.

  • L'agent tire, il ne reçoit rien : aucun port entrant, aucun serveur local qu'une page web pourrait joindre ; HTTPS sortant seulement.
  • Enrôlement comme un terminal : POST /postes rend un code à usage unique de 10 caractères, l'agent s'enrôle par POST /auth/terminaux/enrolement avec le type « poste » (colonne terminal.type = terminal | poste). Ensuite, HTTP Basic (identifiant et secret d'appareil) ; chaque appel vaut battement.
  • Travaux (table travail_poste) : le serveur dépose une lecture de carte ou une opération du composant pour un poste du cabinet dont les capacités le permettent ; l'agent la prend sous bail (POST /postes/agent/travaux/prendre, FOR UPDATE SKIP LOCKED), puis …/terminer ou …/echec. États en_attente → pris → termine | echoue, ou expiré. Idempotent par (cabinet, cle) : une opération rejouée rend le même travail. Ni code porteur ni secret dans les paramètres ; le résultat d'une lecture de carte est effacé une fois remis.
  • Délais (app/postes.py) : poste en ligne si vu depuis 90 s (battement toutes les 30 s), 10 s pour prendre un travail, bail de 30 s ; l'appelant attend 40 s, puis 504.
  • Blocages rendus avant tout dépôt : hors_ligne, lecteur_absent, fente_absente, composant_absent, composant_obsolete (version minimale 2.0), fonction_absente.
  • Démonstration : l'interrupteur agent_poste du registre (en_ligne, hors_ligne, lecteur_absent, composant_obsolete) fait passer SESAM-Vitale par SesamParPoste et l'agent simulé, qui tourne dans le processus de l'API sur le composant factice ; le code porteur se saisit alors au lecteur du poste. Le test de contrat tests/test_sesam_contrat.py passe à travers lui ; il sera le critère d'acceptation de l'agent réel. Tests : tests/test_agent_de_poste.py.

Une seule horloge

« Aujourd'hui », l'instant d'une signature, un horodatage refusé dans le futur, la démonstration posée à l'heure qu'il est : tout lit app.horloge. TABSANTE_HORLOGE="HH:MM" recale l'horloge sur cette heure de Paris, ce jour-là, puis la laisse courir ; now() de la base est recalé d'autant (maintenant_sql : lignes écrites par l'ORM, chaîne d'audit, journal des accès). La variable est refusée hors développement dès l'import. La suite de tests se rejoue ainsi à 0 h 30, 7 h ou 23 h 45 sans attendre l'heure.

Authentification des appels

  • Authorization: Bearer <jeton d'accès> sur toutes les routes internes ; le jeton porte sub, cab (cabinet), role, sid (session), jti, typ="acces". Chaque requête relit la session : une révocation est immédiate.

Keycloak + CPS / Pro Santé Connect réels sont attendus (D-02).
  • Agent de poste : authentification HTTP Basic (identifiant et secret d'appareil du poste enrôlé) sur /postes/agent/* ; secret faux → 401, poste révoqué → 403 (§2).
  • Portail externe : en-tête X-Acces-QR (jeton du QR) + jeton Pro Santé Connect.
  • Idempotency-Key (facultatif, toute écriture POST, PUT, PATCH, DELETE avec un jeton) : le poste fixe en pose une par saisie. La même clé rejouée par la même session rend la réponse réussie gardée (en-tête Idempotency-Replayed: true) sans rien écrire ; un second envoi simultané attend le premier ; la même clé pour une autre demande est refusée (422) ; un refus n'est pas retenu, la saisie corrigée repart avec la même clé (§8). /sync garde ses identifiants d'opération (§9).

Erreurs : detail pour l'humain, regle pour la machine

Un refus métier lève Refus (app/commun.py, sous-classe de HTTPException) ; le gestionnaire rend :

# backend/app/domaines/materiel.py
raise Refus(422, "Numéro de lot à renseigner", regle="INJ-RG-06")
# réponse
HTTP 422
{"detail": "Numéro de lot à renseigner", "regle": "INJ-RG-06"}
  • detail est écrit pour l'utilisateur, sans code du CDC ; regle porte l'identifiant de l'exigence (EX-…, …-RG-nn, HAB-xx, D-nn, CV-nn, OFF-nn) pour l'audit et les clients. Un droit manquant rend 403 avec regle « HAB-xx, §3.2 ».
  • Session : RefusSession rend 401 {"detail", "code", "motif_revocation"?}, code ∈ session_expiree, session_revoquee, terminal_revoque, jeton_rejoue.
  • Codes employés : 401, 403, 404 (hors cabinet ou hors portée), 409 (conflit : identifiant déjà employé, occurrence déjà servie, version de brouillon), 410, 413 (brouillon trop gros), 415 (format illisible), 422 (règle métier, validation ; clé d'idempotence reprise pour une autre saisie, regle « IDEMPOTENCE »), 429 (débit, Retry-After: 60), 502 (télétransmission indisponible), 503 (OCR absent ; panne simulée d'un service, §15), 504 (agent de poste sans réponse dans le délai) ; succès 200, 201, 204. Un 409 dit aussi un conflit de l'aperçu des passages validé sans motif de dérogation (§12), une attribution qui recouvre une absence ou un fichier illisible (§8).
  • Un lot refusé par le contrôle de cohérence rend 409 avec un detail structuré : {message, anomalies, forcable, verifications}.
  • Le poste fixe affiche les erreurs en ambre (jamais en rouge) et retire tout code de spécification (sansCode) ; le terminal range un refus de /sync dans « À corriger » (§9).

8Sécurité

Jetons et sessions

  • Jeton d'accès JWT HS256, 15 minutes (720 en développement), secret TABSANTE_JWT_SECRET de 32 caractères au moins hors développement.
  • Jeton de rafraîchissement opaque (token_urlsafe(32)), gardé haché (SHA-256), à usage unique et tournant : chaque POST /auth/rafraichir rend une nouvelle paire ; validité glissante de 7 jours ; session plafonnée à 30 jours.
  • Rejeu : le jeton immédiatement précédent rejoué dans les 30 secondes (réponse de rotation perdue) rend la même paire ; toute autre réutilisation révoque la session (401 jeton_rejoue).
  • Révocation : POST /auth/deconnexion, POST /auth/sessions/{id}/revocation, POST /auth/terminaux/{terminal}/revocation (terminal perdu) ; GET /auth/sessions liste les sessions.
  • Limitation de débit tenue en base depuis le 15 octobre (table tentative_limitee, migration 0040q) : le plafond vaut pour tous les processus de l'API et survit à un redémarrage ; par adresse et par route : 10 appels par minute (300 en développement) sur /auth/rafraichir, l'enrôlement, /audit/verification, POST /audit/ancre, /dev/*, /externe/* et les routes ouvertes de /simulation ; au-delà, 429. Deux appels simultanés peuvent dépasser le plafond d'une unité (limite assumée dans le code).
  • Poste fixe : jetons en sessionStorage (tabsante.jeton, tabsante.rafraichissement) ; un 401 « expiré » déclenche un seul rafraîchissement partagé puis rejoue la requête.
  • Connexion par carte CPS simulée (mode démonstration seulement, boucle locale, limitée en débit) : POST /simulation/cps/connexion {carte, code, terminal?, secret_terminal?} ; la carte signe un défi, un jeton Pro Santé Connect factice est émis puis vérifié par PscFactice, et la session ouverte est une session ordinaire. Code porteur de démonstration ••••, trois codes faux bloquent la carte (§15). Le mode démonstration est refusé hors développement : ses cartes ouvrent des sessions à qui les présente.
Pas de route de connexion de production : Keycloak + CPS / Pro Santé Connect sont bloquants avant toute donnée réelle (AIPD, INT-05). Hors développement, le bouchon PscFactice refuse toute identité (« Pro Santé Connect n'est pas raccordé ») et n'émet aucun jeton.

Double envoi : clé d'idempotence (Idempotency-Key)

  • Middleware app/idempotence.py, monté au plus près des routes : pour une écriture (POST, PUT, PATCH, DELETE) qui porte l'en-tête et un jeton, la clé est liée à la session (empreinte de la session et de la clé du client) et à la demande (méthode, chemin, paramètres et corps).
  • Verrou consultatif sur la clé : un second envoi identique attend le premier, puis reçoit sa réponse sans rien écrire. Réponse réussie (2xx) gardée 24 h dans requete_idempotente (au-delà de 2 Mo, non gardée : l'envoi rejoué la refait) ; un refus ou une erreur n'est jamais retenu. Même clé pour une autre demande : 422.
  • Poste fixe (web/src/api/client.ts) : une clé par saisie, envois identiques simultanés regroupés côté client, boîte de dialogue désactivée pendant l'envoi. CORS admet l'en-tête. Sans clé ou sans jeton, rien ne change.
  • Tests : tests/test_idempotence.py, web/src/test/DoubleEnvoi.test.tsx.

Enrôlement des terminaux

  1. Au poste fixe (droit HAB-33, page « Terminaux ») : POST /auth/terminaux {"libelle"} rend un code de 10 caractères (alphabet sans 0, O, 1, I), à usage unique, valable ENROLEMENT_MINUTES (10) ; gardé haché ; annulable.
  2. Sur le terminal, sans session : POST /auth/terminaux/enrolement {"code", "terminal", "secret"} — terminal est un UUID stable, secret un secret d'appareil de 256 bits tiré au CSPRNG, rangé dans flutter_secure_storage (Keystore) ; le serveur n'en garde que l'empreinte SHA-256.
  3. Toute session ouverte sur ce terminal lui est liée ; chaque rafraîchissement présente terminal et secret_terminal. Un terminal révoqué n'ouvre ni ne rafraîchit plus aucune session (401 terminal_revoque) : il faut un nouvel enrôlement.

En développement, /dev/demo?terminal=… enrôle d'office un terminal inconnu sans secret (refusé hors développement) ; un terminal révoqué y reste refusé.

  • Contenu : saisies, signatures, cotations, transmissions, exports, connexions et reprises de session, révocations, enrôlements, synchronisations (comptes par type, jamais le contenu), demandes des patients.

Identifiants seulement, jamais le contenu. Fichiers chiffrés au repos (stockage.py)

  • Concerne tout ce que photos.stocker range sous TABSANTE_PHOTOS_DIR : photos, ordonnances photographiées, PDF produits et reçus, BSI déposés, photo de l'entrée du domicile. La base PostgreSQL n'est pas chiffrée par l'application (chiffrement du volume exigé de l'hébergeur HDS).
  • Enveloppe : une clé aléatoire de 256 bits par fichier, enveloppée par la clé maîtresse active d'un port Kms (active, envelopper, desenvelopper) ; contenu AES-256-GCM par segments de 64 Kio, le rang du segment et la marque du dernier entrent dans le nonce. En-tête TSF1. Un fichier altéré, tronqué, réordonné ou dont la clé manque est refusé (409 « Fichier illisible »), jamais servi à moitié. Le nom reste l'empreinte SHA-256 du clair, revérifiée à chaque lecture de document.
  • KMS simulé : KmsLocal, trousseau JSON désigné par TABSANTE_STOCKAGE_TROUSSEAU (défaut var/kms/trousseau_stockage.json), créé au premier usage en développement ; hors développement, l'API refuse de démarrer sans lui. En production : le KMS ou le HSM de l'hébergeur, même port. Sans trousseau, des fichiers restaurés sont illisibles : il se garde hors du serveur, comme la clé de sauvegarde.
  • Commandes (scripts/stockage.py) : nouvelle-cle, migrer [--essai] (chiffre en place les fichiers hérités en clair, lisibles jusque-là), tourner [--essai] (réenveloppe les clés de fichier sous la clé active), verifier (code 1 au moindre fichier illisible), retirer <kid>. Lecture en flux par GET /photos/{id}/fichier. Tests : tests/test_stockage.py.

Sécurité du terminal

  • Base locale chiffrée : chaque enregistrement sembast chiffré en AES-256-GCM (nonce aléatoire de 96 bits par écriture, étiquette de 128 bits, codec tabsante-aes256gcm-1) ; clé de 256 bits tirée au CSPRNG, rangée dans flutter_secure_storage (Keystore Android). Terminal web de démonstration : clé dans le stockage local du navigateur, démonstration seulement.
  • Photos en fichiers chiffrés (coffre.dart) : hors de la base, une photo par fichier sous photos_chiffrees/ (dossier de support de l'application), AES-256-GCM avec la clé de la base (nonce de 12 octets ‖ chiffré ‖ étiquette de 16 octets), écrite en .tmp puis renommée ; magasin sembast fichiers pour le terminal web. Les photos déjà en base sont déplacées au premier lancement (migrerPhotos).
  • Base illisible : nouvelle tentative (3 essais), copie de secours si des lignes sont illisibles, mise en quarantaine du fichier (renommé .quarantaine-<UTC>, jamais supprimé) si la clé manque ou l'en-tête est faux ; écran dédié.
  • Verrou de l'application : code à 6 chiffres (PBKDF2-HMAC-SHA256, 60 000 itérations, sel de 16 octets ; suites et répétitions refusées), 5 essais puis attente doublée de 30 s jusqu'à 15 min, rien n'est jamais effacé après des échecs ; verrouillage au lancement, au passage en arrière-plan et après 5 minutes sans toucher l'écran ; empreinte digitale facultative (invalidée si les empreintes changent). Un appareil sans verrouillage d'écran est refusé.
  • Android : FLAG_SECURE (ni capture ni vignette), allowBackup=false, mode kiosque optionnel (§18).
  • Révocation (401 terminal_revoque, session_revoquee, jeton_rejoue) : précharge, brouillons et jetons effacés ; la file reste chiffrée si elle n'est pas vide, puis « Envoyer d'abord » (réenrôlement) ou « Effacer sans envoyer » ; file vide : base et clé détruites.
  • Signature : empreinte SHA-256 calculée par le serveur à la réception ; en démonstration, signature par carte CPS simulée en plus (ci-dessous), y compris hors connexion ; carte réelle, lecteur du terminal et TEE bloqués (matériel absent).

9Hors connexion et synchronisation

Précharge

GET /terminal/precharge?date= rend la journée : tournées, occurrences, patients (derniers actes, traitement, signaux, rappels, sites récents, compteurs et cotations prévues), plaies, dispositifs, notifications, échanges. Le terminal complète par patient (prescriptions, fréquences, objets clos, contexte de nursing, ordonnances, prescriptions infirmières, prélèvements à faire, résultats, protocoles, accords préalables, données, compétences, bilan de prévention, et depuis le 15 octobre ses demandes de renouvellement d'ordonnance) et globalement (/moi, intervenants, planning, référentiels embarqués, transmissions, tournée du jour, séances et consultations, « Comment faire ? »). Depuis la tournée géolocalisée, la précharge porte aussi itineraires (un plan par tournée et par moment : ordre, repères des domiciles, trajets et heures estimés, « Avant d'arriver ») et geolocalisation (le consentement de l'intervenant au partage de sa position) ; depuis le 15 octobre, « Avant d'arriver » y joint les prérequis de chaque passage (§12) et la photo de l'entrée du domicile, gardée chiffrée sur le téléphone avec les clichés de la précharge. La recherche hors connexion du terminal (§11) ne lit que cette précharge. Rechargée à la connexion, sur « Recharger », après une synchronisation acceptée ou quand la précharge date d'un autre jour ; un bandeau prévient au-delà de 2 heures. Rafraîchie aussi toutes les 5 minutes (tous les 15 cycles de synchronisation de 20 s, cyclesFraicheur) et au retour au premier plan : le terminal relit la seule précharge, en compare l'empreinte SHA-256 (sans les compteurs des dispositifs calculés à l'instant) à celle de la dernière précharge complète, et ne relit la suite (prescriptions, dossiers…) que si elle a changé. La précharge est tracée au journal des accès, patient par patient.

Garanties de la synchronisation

  • Une opération, un SAVEPOINT : un refus n'emporte pas les autres ; un seul commit en fin de lot ; une entrée chaînée synchronisation (comptes par type).
  • Envoi rejoué pendant le premier (réponse perdue, le terminal renvoie la même file) : avant toute lecture, le lot prend un verrou consultatif par opération (pg_advisory_xact_lock(hashtextextended('operation:' || clé, 0))), tous dans un ordre fixe, donc sans interblocage entre deux lots. Le second envoi attend la validation du premier, puis lit ce qu'il a écrit et rend, opération par opération, la même réponse (« déjà reçu ») : ni 500, ni doublon. Une violation d'unicité restante rend 409. Test : tests/test_sync_concurrence.py.
  • Ordre : les opérations de planning (échanges) d'abord (OFF-11), puis l'ordre de la file ; les résultats reviennent dans l'ordre de la file.
  • Idempotence sans table de clés : l'UUID tiré au terminal devient la clé primaire de l'entité. Rejouer signer_acte rend l'acte existant si le même infirmier l'a signé, sinon 409 « Identifiant d'acte déjà employé » ; creer_patient rend 409 si l'identifiant appartient à un autre cabinet ; donnees.id est exigé pour les créations rejouables.
  • Pas de fusion (OFF-08, OFF-09) : la remontée est fidèle ; un doublon ou une occurrence déjà servie rend 409. Les cas résiduels acceptés sont marqués dans les faits de l'acte (hors_connexion : fréquence arrêtée après le soin, échange reçu hors connexion).
  • Date du geste (_date_du_geste) : la date propre de l'opération (realise_le, ouvert_le, cloture_le…), avec fuseau obligatoire, sinon cree_le (au plus 5 minutes dans le futur) ; c'est elle que juge la portée d'un remplaçant.
  • Saisie différée (OFF-13 à OFF-18) : au-delà de SEUIL_DIFFERE_MINUTES (120, provisoire D-04) entre réalisation et saisie, l'acte est marqué « différé », motif_differe est exigé (sinon 422), et une validation au poste fixe (validation_differe : a_valider → validee ou refusee) est due, par un autre que le signataire (droit OFF-16) ; un refus retire la cotation. File : GET /saisies-differees.
  • Remplaçant : un geste mis en file avant l'ouverture de sa session, ou daté de plus de 120 minutes avant sa mise en file, est refusé (regle CV-09) ; un geste hors de la période active rend 403.
  • Lectures groupées (app/lot.py) : chaque donnée de signature est lue une fois pour tous les patients du lot. Depuis le 15 octobre (NFR-08), les actes d'un passage sont lus une fois par lot (la relecture d'un patient périmé est servie jusqu'à la prochaine écriture du lot) et l'avis de changement du poste fixe part une fois par transaction, non plus à chaque SAVEPOINT : au volume de référence, un /sync de 50 actes passe de 533 à 383 requêtes, celui du garde-fou (12 actes) de 140 à 117, et le nombre de requêtes ne dépend plus de la longueur des passages (test_perf_fumee.py::test_sync_constante_quand_le_passage_s_allonge). Restent deux lectures par acte signé dans la cotation par passage.
  • Fréquence ponctuelle créée au terminal : mêmes contrôles d'aperçu qu'au poste fixe (absence, heure fixe déjà prise…) ; un conflit bloquant exige motif_derogation, sinon 409 (§12).

Côté terminal : file, refus, brouillons

  • Synchronisation toutes les 20 secondes et après chaque signature, par lots de 500, dans l'ordre des signatures, planning d'abord ; précharge réévaluée tous les 15 cycles (5 minutes).
  • « ok » retire l'opération ; un refus reste en file, avec son motif lisible (codes retirés à l'écran), et est retenté à chaque passe. L'onglet Envois montre d'abord « À corriger » : Corriger et renvoyer (la nouvelle signature remplace la refusée au même rang) ou Abandonner (avec confirmation, emporte les opérations qui en dépendent). Les refus de délai (CV-09, D-04) ne se corrigent pas, ils s'abandonnent.
  • Brouillon local enregistré à chaque appui (par plaie, par patient et fiche, ou par dispositif), effacé atomiquement à la signature.
  • Brouillon partagé (fiche 24 : consultation, séances art. 5 ter et RAAC) : un par occurrence, GET|PUT /occurrences/{id}/brouillon avec version (table brouillon_sous_fiche). Versions divergentes → 409 nommant qui l'a enregistré et quand ; le terminal bloque la signature (« Il manque : choix du brouillon ») jusqu'à « Garder le mien » ou « Reprendre le leur ». Au-delà de 200 000 octets → 413. Le brouillon s'efface de lui-même quand l'occurrence n'est plus due (trigger, migration 0034).
  • Quarantaine : mécanisme du terminal seul (base locale illisible, §8) ; il n'y a pas de quarantaine côté serveur.
  • Le changement d'intervenant sur un terminal est refusé tant que la file, les photos ou les brouillons ne sont pas vides.

Cotation provisoire hors connexion (démonstration)

Calculée seulement hors connexion (en ligne, le serveur cote à la réception), jamais pour une aide-soignante, à la signature ou à la correction. Le terminal lit la plage cotation_prevue préchargée qui contient l'heure réelle du soin, et seulement si l'acte signé répond comme le passage rejoué (anticoagulant, injection, prélèvement, constantes, pansement sans Redon). Sinon : « Cotation provisoire non estimée hors connexion · le cabinet la calcule à l'envoi », rien ne part, aucun décompte local. Toujours étiquetée « Démonstration ». Compteurs aux trois échelles ; le résultat reconfirmé et l'écart éventuel sont expliqués au retour. Depuis le lot E, chaque ligne suit la cotation v2 (§14) : statut, taux, quantite, nature, regles ; facturable() dit ce qui est facturé, l'affichage lit « IK 1 · 12 km » ou « à 50 % ».

Ordre de passage proposé (ordonnancement.py)

« Proposer un ordre » : plus proche voisin depuis le point de départ, puis amélioration locale (2-opt : inverser un tronçon ; déplacement d'un arrêt) tant que la tournée raccourcit, 60 passes au plus. Coût : chaque minute hors fenêtre pèse 1 000 (une fenêtre tenue passe avant toute minute de route gagnée), une minute de retard sur une heure fixe pèse vingt minutes hors fenêtre, puis l'heure de fin. Les passages à heure fixe ne bougent jamais et restent dans l'ordre chronologique ; les autres s'arrangent autour. Une suggestion, jamais une consigne : rien n'est enregistré sans validation (glisser-déposer ou flèches au poste fixe, « Garder cet ordre par défaut »). Tables ordre_passage (ordre d'un jour, ou par défaut, date nulle) et passage_fixe (heure fixe d'un jour ou habituelle).

14Facturation (démonstration)

Tout le circuit de facturation tourne sur des doublures : moteur MoteurDemo (version demo-0.3, simulation() vrai), cartes CPS et Vitale simulées et adaptateur SesamVitaleFactice (version factice-0.2, numéros SIM-…, aucun organisme ; retours NOEMIE, tiers payant et pièces SCOR simulés), en direct ou par l'agent de poste simulé. Toute FSE est marquée simulée. Le poste fixe affiche un bandeau permanent.

Du soin signé au retour de l'Assurance maladie

  1. Signature : le serveur cote à la réception (port Moteur, par passage depuis la cotation v2, ci-dessous) ; la cotation provisoire du terminal est gardée si elle a été envoyée (hors connexion, §11). Chaque cotation porte la version du moteur, du référentiel de règles et des tarifs retenus.
  2. Reconfirmation (POST /facturation/cotations/confirmer) : le moteur rejoue le passage entier ; résultat identique → confirmee ; écart ou règle du cabinet → controle. Jamais de correction silencieuse. Lectures groupées (reconfirmation_groupee) : patients, cabinets, objets suivis et prescriptions lus une fois, compteurs verrouillés une fois et écrits en fin de lot ; environ 190 actes passent de 6 900 requêtes et 14 à 21 s à 415 requêtes et environ 1 s.
  3. File de contrôle (cotation/controle.py, réglages D-05 du cabinet) : cumul, majoration et au_dela_frequence actifs par défaut, non_programme et saisie_differee inactifs ; divergence et correction toujours en file. Arbitrage (confirmer ou ecarter, motif exigé) sous 7 jours par un IDE titulaire, en structure ou responsable.
  4. FSE (POST /facturation/fse, HAB-23) : créée par l'infirmier qui a réalisé les actes (émetteur : ce signataire en libéral, la structure en structure), puis sécurisée (POST /facturation/fse/{id}/securiser) : en démonstration, par la carte CPS de l'exécutant et la lecture de la carte Vitale (mode vitale), ou sans Vitale (mode degrade : feuille papier à adresser à la caisse) ; la carte signe la charge de la FSE (empreintes du patient et des actes) ; la marque hors_connexion est gardée pour une FSE sécurisée au domicile. Tiers payant de démonstration : part obligatoire 60 % (100 % en cas d'exonération), part complémentaire demandée par DRE. Annulable avant le lot.
  5. Lot (POST /facturation/lots, HAB-24) : contrôle de cohérence avant envoi (EX-TB-07) ; forçage possible avec motif, sauf anomalies actes_signes et differe_non_valide ; refus en 409 détaillé.
  6. Télétransmission (pièces SCOR jointes au lot) puis retours (POST /facturation/lots/{id}/retours, HAB-25) : chaque FSE devient acceptee ou rejetee ; le lot est clos quand tous ses retours sont là. Dans la réalité, les retours arrivent par NOEMIE ; ici l'adaptateur factice les produit, avec le paiement d'une FSE acceptée (référence et date du virement de la part obligatoire, DRE payée ou refusée ; refusée, sa part revient au patient, à recouvrer). Montants de démonstration.
  7. Rejet (POST /facturation/fse/{id}/rejet) : refacturer ou abandonner.

Moteur de cotation v2 (démonstration) et banc de cotation

Toujours une doublure : ces règles reproduisent la NGAP pour la démonstration et les tests ; le moteur réel est celui de TABSANTE, derrière le même port.
  • Contrat (cotation/interface.py) : Moteur.coter_passage(entrees) → list[SortieCotation], regles(version) (référentiel des règles, exposé par GET /facturation/regles-cotation aux infirmiers, HAB-22) et coter_depot_bsi(…). MoteurDemo, version demo-0.3.
  • Cotation par passage : le moteur cote un passage entier — même patient, même jour (Paris), même moment, même intervenant et même séance ; un écart de plus de 2 h ouvre un autre passage. L'ordre de signature ne compte pas (actes triés par heure de réalisation). Le stockage reste une ligne cotation par acte, qui garde les lignes que le passage lui donne ; la migration 0039b ajoute cotation.version_regles, cotation.version_tarifs, ligne_fse.taux et ligne_fse.quantite.

Une ligne JSON en sortie ; code 0 conforme, 1 chaîne (d'audit ou des accès) rompue, ancre divergente ou fichier d'ancres disparu (rien n'est alors ancré ni recopié), 2 dépôt en échec.
