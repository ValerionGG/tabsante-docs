En revanche, deux bombes à retardement casseront la suite pour tous les lots sans changement de code : le 1er novembre 2026 (test_series_de_sites_du_patient_toutes_fiches) et le 1er janvier 2027 (test_contexte_chimio_actif_a_la_date). Voir P1-5. Trois fragilités s'y ajoutent : - 10 modules de test figent « aujourd'hui » à l'import ; - 3 tests lisent l'heure murale ; - des compteurs calculés à l'heure murale sont comparés entre deux lectures. - Synchronisation hors connexion. La remontée tient bien sous les entrées malformées : 1 320 opérations malformées (33 types × 5 contextes × 8 variantes), aucune erreur 500, aucune file bloquée. Le rejeu est idempotent et un double passage est refusé proprement (409). Deux défauts sont prouvés : - P1-1 : la file d'un remplaçant mise en attente avant une reconnexion est refusée pour toujours (CV-09) ; - P2-1 : une opération rejouée avec un autre contenu est déclarée « ok » sans rien changer. - CI. Les deux définitions (GitHub, GitLab) reprennent verifier_tout. Il leur manque : - l'intégration du terminal contre l'API (47 tests, jamais en CI) ; - une garde du contrat OpenAPI, dont dépendent les deux clients ; - un lint Python ; - le site public ; - des versions épinglées (actions, images, uv).

Aucun secret n'est requis. Aucun chemin Windows ne casse sous Linux (casse des imports, fins de ligne, bit exécutable vérifiés). - Performance. Les 211 lectures GET mesurées sur trois jeux de volume réduits ont un nombre de requêtes constant quand les patients (10 → 40) ou l'historique (4 → 16 jours) grandissent, sauf deux : - /previsionnel : une lecture par jour (13, puis 62, puis 230 requêtes pour 1, 8 et 32 jours), sans garde-fou ; - /simulation/cartes/vitale : une lecture par patient.

/sync reste à ~6 requêtes par acte. Mais son temps croît plus vite que le lot, et sous charge un lot de 200 actes dépasse le délai de 15 s du terminal. Un défaut d'API est trouvé en passant : GET /plaies/{id} répond 500 avec l'identifiant d'un cathéter (P2-14). - Fiabilité de la vérification. La suite du serveur dure 1 h 39 sur ce poste. 70 tests (5,5 %) en prennent la moitié : 66 sèment la démonstration complète (POST /dev/demo, ~9 800 requêtes chacun). Deux échecs observés ne viennent que de la charge, sans lien avec le code : un plafond de temps et un minuteur de 20 s dans un test de widget. Surtout, le conteneur PostgreSQL partagé ne supprime plus ses bases : des DROP DATABASE attendent jusqu'à 3 h un point de contrôle (P1-4).

1. Dépendance à l'heure, au jour et à l'ordre

Ordre. pytest-randomly n'est pas installé : -p no:randomly n'a donc pas d'objet. L'ordre aléatoire vient du greffon d'audit, qui mélange les 1 268 éléments avec une graine commune aux trois processus xdist (le dispatch reste cohérent). Résultat : 1 seul échec, test_formes_lectures.py::test_dispositifs_du_cabinet_en_une_lecture. Rejoué seul à 4 heures différentes (réelle, 07:00, 10:45, 00:30), il passe. 3. CI et vérification complète

Relus : scripts/verifier_tout.ps1, scripts/verifier_tout.sh, .github/workflows/ci.yml, .gitlab-ci.yml, docs/exploitation/integration-continue.md. Les deux scripts et les deux CI font les mêmes étapes, à une exception près : la garde de l'horloge ne tourne que la nuit en CI. Le nettoyage des bases jetables est correct (préfixe commun, WITH (FORCE)) et les variables TABSANTE_* du shell sont isolées.

Mode -Rapide : dès qu'un fichier de backend/ change, il rejoue toute la suite du serveur (1 h 39 ici). Le crochet pre-push n'est donc pas rapide pour un lot serveur (P2-8).
